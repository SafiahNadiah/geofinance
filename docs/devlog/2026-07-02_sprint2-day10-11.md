## 3. Bugs Found & Fixed (chronological)

### Bug 1 — Duplicate customer emails

**Symptom:** `\copy customers` failed partway through with
`duplicate key value violates unique constraint "customers_email_key"`
at row 590.

**Cause:** `generate_seed_data.py` used `fake.email()` (Faker's
standard, non-unique generator) for 2,000 customers — a collision was
statistically likely at that volume.

**Fix:** changed to `fake.unique.email()`. Verified via pandas:
`df['email'].duplicated().sum() == 0` across all 2,000 rows.

---

### Bug 2 — UUIDs are not deterministic across generator re-runs

**Symptom:** after Bug 1's fix, only the updated `customers.csv` was
copied into the container. Re-running the import failed with
`insert or update on table "customers" violates foreign key
constraint "customers_nearest_branch_id_fkey"` — the branch UUIDs
referenced in the new `customers.csv` didn't exist in the (stale)
`branches.csv` still sitting in the container.

**Cause:** `random.seed(42)` makes Python's `random` module
deterministic, but `uuid.uuid4()` does **not** use that module — it
draws from `os.urandom()`. Every re-run of the generator produces
**entirely new UUIDs** for every entity, even though names/addresses
stay identical.

**Fix:** copy the **entire** `output/` folder into the container after
any regeneration, never a single file — e.g.
`docker cp database/seed-data/output/. geofinance-postgres:/tmp/seed-data/output/`.
Documented as a standing rule for future regenerations.

---

### Bug 3 — `psql` not available on the Windows host

**Symptom:** running `import.sh` directly from Git Bash on Windows
failed immediately: `bash: psql: command not found`.

**Cause:** no local PostgreSQL client tools installed on the host —
all prior successful `psql` calls had actually gone through
`docker exec ... psql`, running *inside* the container, not on the
host.

**Fix:** copied `database/seed-data/` into the container
(`docker cp`) and ran `schema.sql`/`import.sh` from inside the
container instead, where `psql` is already present (bundled in the
`postgis/postgis` image).

### Bug 5 — Password authentication failure connecting from the host

**Symptom:** running `load_risk_zones.py` (a Python/`psycopg2` script,
needed since the container has no `python3`) from the Windows host,
using `DATABASE_URL` built from `.env` values (`postgres:postgres`),
consistently failed: `FATAL: password authentication failed for user
"postgres"`.

**Investigation:**
1. Confirmed `.env` really did contain `DATABASE_PASSWORD=postgres`.
2. Ran `ALTER USER postgres PASSWORD 'postgres';` inside the container
   directly — succeeded (`ALTER ROLE`), but did not fix the host-side
   connection failure.
3. Checked `netstat -ano | findstr :5432` — found **two** processes
   listening on port 5432.
4. `Get-Process` on both PIDs identified one as `com.docker.backend`
   (expected) and the other as a plain `postgres` process.
5. `Get-Service` confirmed a **native PostgreSQL 18 Windows service**
   (`postgresql-x64-18`) was installed and running independently of
   Docker, competing for the same port.

**Cause:** `localhost:5432` connections from the host were being
served by the native Windows PostgreSQL installation (different,
unknown credentials) instead of being forwarded into the Docker
container, because both were bound to the same port.

**Fix:**
```powershell
# (run as Administrator)
Stop-Service -Name postgresql-x64-18
Set-Service -Name postgresql-x64-18 -StartupType Disabled   # prevent recurrence on reboot
```
After stopping the native service, host-to-container connections on
`localhost:5432` succeeded immediately with the `.env` credentials.

**Why this is worth flagging clearly:** this bug would have silently
resurfaced on every PC restart if the service hadn't also been set to
`Disabled`, not just stopped for the current session.

---

### Bug 6 — `ogr2ogr` not available for GeoJSON import

**Symptom:** `import.sh`'s risk zone loading step failed:
`import.sh: line 19: ogr2ogr: command not found`.

**Cause:** the original `import.sh` (written before any container was
actually built) assumed GDAL/`ogr2ogr` would be available — it is not
part of the `postgis/postgis` base image.

**Fix:** replaced that step with a purpose-built
`database/seed-data/load_risk_zones.py` (`psycopg2` +
`ST_GeomFromGeoJSON`), run from the host after resolving Bug 5's port
conflict. `import.sh` and `database/seed-data/README.md` updated to
reflect the new dependency (`psycopg2-binary` via `pip`, not GDAL).

**Minor follow-up noted, not blocking:** the script printed
"Inserted 0 risk_zones rows" despite the data actually loading
correctly (`SELECT count(*) FROM risk_zones` returned 12, matching
expected). Likely a cosmetic bug in how the script reports its own
`rowcount` after an `ON CONFLICT`-style insert — tracked as a small
cleanup item, not re-blocking since the data itself is verified
correct directly against the database.

## 4. Final Verification

### 4.1 Row counts — all 5 tables

```powershell
docker exec -it geofinance-postgres psql -U postgres -d geofinance -c "SELECT 'branches' t, count(*) FROM branches UNION ALL SELECT 'customers', count(*) FROM customers UNION ALL SELECT 'properties', count(*) FROM properties UNION ALL SELECT 'loans', count(*) FROM loans UNION ALL SELECT 'risk_zones', count(*) FROM risk_zones;"
```

| Table | Expected | Actual |
| --- | --- | --- |
| branches | 18 | ✅ 18 |
| customers | 2,000 | ✅ 2,000 |
| properties | 1,200 | ✅ 1,200 |
| loans | 900 | ✅ 900 |
| risk_zones | 12 | ✅ 12 |

### 4.2 Geometry spot-check

```powershell
docker exec -it geofinance-postgres psql -U postgres -d geofinance -c "SELECT code, ST_AsText(geom) FROM risk_zones LIMIT 3;"
```

Returned valid `POLYGON(...)` geometry with coordinates correctly
within the Klang Valley reference area for all 3 sampled rows.

### 4.3 FK integrity spot-check (manual, earlier in session)

Picked one `loans` row and confirmed via `Select-String` that its
`customer_id` and `branch_id` UUIDs existed as real rows in
`customers.csv` and `branches.csv` respectively — later reconfirmed
implicitly by the fact that the full `\copy loans` succeeded (FK
constraints would have rejected any row with a dangling reference).
