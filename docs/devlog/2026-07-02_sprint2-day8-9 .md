## 2. Migration Tool Decision

`docs/02_SRS.md` left the migration tool as an open decision between
`node-pg-migrate` and Prisma Migrate. **Chose `node-pg-migrate`** —
reasoning: `03_DATABASE.md`'s table definitions are already written in
raw-SQL-style terms (explicit `GEOMETRY(Point,4326)` types, `CHECK`
constraints), and `node-pg-migrate` maps to that directly without
fighting an ORM's schema DSL over PostGIS-specific types.

This decision closes the open item flagged in `03_DATABASE.md §6`
("Migration Strategy").

### 4.3 Foreign key sanity check — bug found and fixed

```powershell
docker exec -it geofinance-postgres psql -U postgres -d geofinance -c "\d loans"
```

**First run** revealed a bug: only `branch_id` had a proper `FOREIGN
KEY` constraint (`loans_branch_id_fkey`). `customer_id` and
`property_id` had only regular btree indexes
(`idx_loans_customer_id`, `idx_loans_property_id`) — an index is not
the same as a foreign key; nothing was preventing a `loans` row from
referencing a non-existent customer or property. This violated
`03_DATABASE.md §3.5`, which specifies FKs on all three columns.

**Root cause:** migration `0006_create_loans_table.js` created indexes
on `customer_id`/`property_id` but omitted the `references` clause for
those two columns (only `branch_id` had it wired correctly).

**Fix:** per the migration rule in `03_DATABASE.md §6` ("never edited
after merge, write a new migration to amend"), migration `0006` was
**not** edited directly. Instead, a new migration
`0011_fix_loans_foreign_keys.js` was added with `ALTER TABLE loans ADD
CONSTRAINT ... FOREIGN KEY ...` for both missing columns, then applied
with `npm run migrate:up`.

**Re-verified** — `\d loans` after the fix confirmed all three FKs present:
```
Foreign-key constraints:
    "loans_branch_id_fkey" FOREIGN KEY (branch_id) REFERENCES branches(id)
    "loans_customer_id_fkey" FOREIGN KEY (customer_id) REFERENCES customers(id)
    "loans_property_id_fkey" FOREIGN KEY (property_id) REFERENCES properties(id)
Referenced by:
    TABLE "loan_risk_assessments" CONSTRAINT "loan_risk_assessments_loan_id_fkey" FOREIGN KEY (loan_id) REFERENCES loans(id)
```

`loan_risk_assessments.loan_id → loans.id` was also confirmed correct
as a bonus check.

**Why this mattered:** without this fix, the database would silently
accept a loan referencing a customer or property that doesn't exist —
a data integrity risk that could have gone unnoticed for many sprints
until it caused a subtle bug much later (e.g. a spatial query or risk
calculation silently failing on an orphaned loan). Catching it here,
at schema creation time, was much cheaper than catching it after
Sprint 7's risk-scoring logic was built on top of this table.
